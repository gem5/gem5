# Gem5 Bazel adoption

This document outlines the adoption of Bazel as an alternative build tool for
gem5. The term 'bazelization' will be used to refer to the implementation of
this build system.

## Design Goals

1.  **Non-Invasive Integration:** Implement Bazel alongside SCons without
    modifying existing SConscripts or other project files.
1.  **Simplified Maintenance:** Ensure BUILD file maintenance is as
    straightforward as maintaining SConscripts.
1.  **Generic Rules Preference:** Prioritize standard Bazel rules over
    gem5-specific rules to facilitate knowledge transfer and maintainability.

## Current Status

Bazel can build an executable capable of running
`configs/learning_gem5/part2/run_simple.py`, indicating a core gem5 simulation
framework is functioning. Build configuration is currently fixed and hardcoded.
CPU support is pending the integration of the ISA code generator with Bazel
rules.

### Build Procedure

1.  **Configure:** Generate `build/bazelrc` from a `.config` file created via
    Kconfig. This file maps SConscript `HAVE_XXX` and `USE_XXX` switches to
    Bazel configurations. (See [Configuration](#Configuration) for details.)
    Note the script at this point can only produce fixed output, and the python
    version is hardcoded to be 3.11.

    -   `bash bazel run //build_tools/bazel:config -- $(realpath
        ./path/to/.config)`

1.  **(Optional) Regenerate BUILD Files:** This step is only required after code
    modifications, as generated BUILD files are committed to the repository.
    **Caution:** This process executes SConscripts and SimObject `.py` files.

    -   `bash bazel run @bazelize_gem5//scons2bzl:sync --
        --allow-code-execution`

1.  **(Optional) Build Executable:** (This step can be skipped, as `bazel run`
    will trigger a build if the executable is missing.)

    -   `bash bazel --bazelrc=build/bazelrc build //src:gem5`

1.  **Run Simulation:**

    -   `bash bazel --bazelrc=build/bazelrc run //src:gem5 -- $(realpath
        ./config/learning_gem5/part2/run_simple.py)`

1.  **Run Test:** This executes the simulation identical to the previous step
    and performs basic output validation.

    -   `bash bazel --bazelrc=build/bazelrc test //tests/bazel:run_simple`

## Configuration

Gem5 had implemented system environment inspections with SCons to determine the
availability of dependencies, and sets `HAVE_XXX` flags accordingly. Bazel BUILD
files are platform agnostic, and the the hermetic build principle implies that
the same build command will always produce the same output. All these
necessitate externalizing platform-specific information, either to generate a
platform dependent file, or to configure the build directly from the
command-line.

We utilize Bazel's [configuration](https://bazel.build/extending/config) feature
to replicate `HAVE_XXX` and `USE_XXX` switches. These are implemented as Bazel
`config_setting` rules, configurable either via command-line flags or a
`build/bazelrc` file (filename subject to change). This file essentially stores
a set of command-line flags representing a specific gem5 configuration instance.

Users can directly specify configuration flags via the command line or use the
`//build_tools/bazel:config` helper script to generate `build/bazelrc` from a
Kconfig `.config` file. The helper script is responsible for package
availability detection, and the `.config` file reflects the user's selection of
features of interest. Refer to `src/generated/flags/BUILD.bazel` for a
comprehensive list of available configuration flags.

## BUILD File Generation

A BUILD file generator, akin to
[Gazelle](https://github.com/bazel-contrib/bazel-gazelle), has been developed
for gem5's bazelization. The tool is written in Python and is located in
`ext/bazelize_gem5` for parsing source code and SConscripts to automatically
generate Bazel BUILD files. This aims for a seamless transition, preserving
standard gem5 development. While the tool is ultimately intended for
obsolescence upon SConscript removal, it is valuable during the current,
potentially extended, transition.

## Hermeticity Considerations

Consider the file `tags.cc`, generated by `util/cpt_upgrader.py`, as an example,
presents a hermeticity challenge. The code generator relies on implicit inputs,
such as files within `/util/cpt_upgraders/*.py`, which are not explicitly
declared in SConscripts. Bazel's strict adherence to
[hermeticity](https://bazel.build/basics/hermeticity) prohibits such implicit
dependencies. Solutions include creating a wrapper for `util/cpt_upgrader.py` to
enforce explicit input specification via the command line, or, preferably,
refactoring the script to achieve true hermeticity.

Currently, `tags.cc` is generated by `stub-tags-cc.sh`, which consistently
produces the same output. While this workaround is acceptable for the current
fixed configuration implementation, a hermetic wrapper remains to be
implemented.

The rest of this section describes the implementation details on how SConscript
declarations are mapped to Bazel targets. For example, [Source](#source)
describes how targets declared as `Source()` in SConscript are reproduced in
Bazel.

### Source

The `cc_library` Bazel rule is used to describe a `Source()` in SConscript. For
instance, `src/sim/fd_entry.{cc,hh}` are declared as one compilation unit in
Bazel:
```
cc_library(
    name = "fd_entry",
    srcs = ["fd_entry.cc"],
    hdrs = ["fd_entry.hh"],
    copts = COMMON_COPTS + [],
    include_prefix = "sim",
    visibility = ["//build_tools/bazel/package_group:simulator"],
    deps = ["//src/sim:serialize"],
)
```

`//src/sim:serialize`, also a `cc_library`, is declared as a dependency
because `fd_entry.hh` includes `serialize.hh`.

This makes a single `.cc` and `.hh` pair to comprise one single compilation
unit. Conversely, creating a monolithic Bazel target encompassing all gem5's
`*.cc` and `*.hh` files presents significant challenges. Specifically, it
disrupts include path resolution, as the include paths would not align with
package (directory) structure, violating Bazel's dependency management
principles. While a middle-ground approach, such as creating larger targets per
directory, is possible, it is discouraged and may undermine the benefits of
adopting Bazel, as outlined in the
[official guideline](https://bazel.build/basics/dependencies#using_fine-grained_modules_and_the_111_rule).

If there's only `foo.hh` without `foo.cc`, the `foo.hh` alone will still be
considered as a standalone target to make all dependent relationship in the
build explicit (which is implicit in SCons).

#### Dealing with circular dependencies

Implementing the above yields the following construct:
```
cc_library(
    name = "a",
    srcs = ["a.cc"],
    hdrs = ["a.hh"],
    deps = [":b"],
    ...
)
cc_library(
    name = "b",
    srcs = ["b.cc"],
    hdrs = ["b.hh"],
    deps = [":a"],
    ...
)
```

This scenario results in a circular dependency, which Bazel strictly prohibits.
If all targets within the loop reside in the same directory, a potential
workaround involves consolidating them into a single target:
```
cc_library(
    name = "a_and_b",
    srcs = ["a.cc", "b.cc"],
    hdrs = ["a.hh", "b.hh"],
    ...
)
```

However, this approach deviates from the
[official guideline](https://bazel.build/basics/dependencies#using_fine-grained_modules_and_the_111_rule),
which advocates for fine-grained targets. Moreover, it fails to address
inter-package circular dependencies. Consequently, an alternative strategy was
implemented, introducing auxiliary targets to break these cycles. For instance:
```
cc_library(
    name = "a",
    srcs = ["a.cc"],
    hdrs = ["a.hh"],
    deps = [":workaround_that_cuts_circular_dependency__b"],
    ...
)
cc_library(
    name = "b",
    srcs = ["b.cc"],
    hdrs = ["b.hh"],
    deps = [":a"],
    ...
)
cc_library(
    name = "workaround_that_cuts_circular_dependency__b",
    srcs = [],
    hdrs = ["b.hh"],
    deps = [],
    ...
)
```

Notably, an additional target, named
`workaround_that_cuts_circular_dependency__b`, was created specifically for
`b.hh`, effectively "cutting" the circular dependency from target `":b"`.

For a comprehensive list of headers manually selected to resolve all identified
dependency loops, refer to `hdrs_cut_circular_dep` in
`ext/bazelize_gem5/scons2bzl/workarounds.py`.

### SimObject

#### The macro

`sim_object()` is defined in `build_tools/bazel/rules.bzl` to declare a
sim-object. `build_tools/bazel/macro.bzl` also defines `macro_sim_object()`
which provides an interface much more similar to SConscript's `SimObject()`.

For example, the following sim-object in `src/sim/SConscript`:
```
SimObject(
    'Workload.py',
    sim_objects=['Workload', 'StubWorkload', 'KernelWorkload', 'SEWorkload'],
    enums=['KernelPanicOopsBehaviour']
)
```

will be mapped to the following in `src/sim/BUILD.bazel`:
```
macro_sim_object(
    "Workload.py",
    enums = ["KernelPanicOopsBehaviour"],
    sim_objects = [
        "Workload",
        "StubWorkload",
        "KernelWorkload",
        "SEWorkload",
    ],
)
```

#### Under the hood

A Bazel `genrule` is programmed to invoke `build_tools/marshal.py` for the
sim-object's `.py` file. Then the resulting `.cc` file will be passed to another
`cc_library` rule for linkage with the main binary.  Similar to
`build_tools/marshal.py`, there are also `genrule`s for
`sim_object_param_struct_{cc,hh}.py` and `enum_{cc,hh}.py`, respectively.

All are implemented within `build_tools/bazel/rules.bzl`.

### PySource

Similar to sim-objects. See `macro_py_source()` from
`build_tools/bazel/marco.bzl`.

### DebugFlag, DebugFormatFlag, and CompoundFlag

These are addressed by two `genrule`s plus one `cc_library`. See `debug_flag()`
from `build_tools/bazel/rules.bzl`.

## Generated File Handling

Under the gem5 build directory, SCons generates code into `params/`, `enums/`,
`config/`, and `debug/` directories. From Bazel's perspective, these directories
are located within `src/generated` (path subject to change). These directories
needs to be presented in the source tree because a BUILD file needs to be
created to mark it as a Bazel package even when all code are generated.

Furthermore, a new directory, `flags/`, has been introduced to `src/generated`
to house Bazel-specific [configuration](#Configure) files.

## The gem5 "main" Executable

The `//src:gem5` target produces the gem5 executable. Its dependencies are
`:lib` targets within `src/` subpackages. These `:lib` targets, `cc_library`
instances, depend on other `:lib` targets as well as object files (those mapped
from SConscript `Source()`). Therefore, the top-level `:lib` and its transitive
dependencies include all objects recursively declared under `src/`.

## Roadmap for the Bazelization

1.  **Proof-of-Concept Implementation (Current Status):**

    *   Limited gem5 feature and configuration support.
    *   BUILD files generated exclusively from SConscripts.

2.  **Bazel as a secondary Build System for gem5:**

    *   Comprehensive gem5 feature and configuration support within Bazel.
    *   BUILD files can be converted from SConscripts
    *   BUILD files can be maintained by developers if certain features are
        intended to be supported in Bazel only

3.  **Full Bazel Adoption:**

    *   Removal of the `scons2bzl` conversion script.
    *   Exclusive developer maintenance of BUILD files.
