# 🛡️ Research Roadmap: Speculative Data Defense (LVP/FLOP)

## Phase 0: Setup and Tooling Environment
Ensure all external visualization, execution tools, and debugging headers are ready for analyzing the pipeline and validating ARM payloads.
- **Konata Visualization**: Download and configure Konata to read gem5 `trace.out` logic generated by the `--debug-flags=O3PipeView` flag. This shows instructions moving across branches.
- **Native ARM Testing**: Use `qemu-user-static` to easily test the `aarch64` C++ payloads on the host machine before executing full simulator cycles.
- **Capstone Disassembly**: Add `libcapstone-dev` to translate raw hex (e.g., `0xb9400001`) into readable assembly (`LDR W1, [X0]`) in the gem5 trace outputs.
- **m5 Utilities**: Incorporate `m5op.h` inside gadget binaries so the C++ code can programmatically dictate when to `m5_reset_stats()` and `m5_dump_stats()`.

## Phase 1: ARM O3 Infrastructure (Current Milestone)
The goal is to transition from the "Simple" verification model to the Out-of-Order engine that supports speculation.
- **Action**: Create a sophisticated Python configuration script using `ArmO3CPU`.
- **Logic**: Configure the pipeline parameters (ROB size, IQ size, and LSQ depth) to match modern high-performance cores.
- **Verification**: Run the "Hello World" ARM binary on the O3 model and verify the pipeline stages in the `config.ini` output.

## Phase 2: LVP Module Development (C++)
You will build the Load Value Predictor as a standalone microarchitectural component.
- **Files**: Create `src/cpu/o3/lvp.hh` and `src/cpu/o3/lvp.cc`.
- **Mechanism**:
  - **PC-Tagged Table**: A structure that stores the last-seen return value for specific load instructions.
  - **Training**: Implement a counter that only enables prediction after observing a constant value for 250 iterations (per the FLOP paper findings).
  - **Heuristics**: Explicitly ignore 8-byte loads to avoid predicting pointers, focusing the vulnerability on "Type" fields and integers.

## Phase 3: Pipeline Integration (The "Surgery")
Integrating the LVP into the core execution flow of gem5's O3 model.
- **Rename Hook (`src/cpu/o3/rename.cc`)**:
  - Intercept load instructions.
  - Query the LVP. If confident, inject the predicted value into the physical register.
  - Mark the instruction as "Speculatively Predicted" for tracking.
- **IEW Hook (`src/cpu/o3/iew.cc`)**:
  - Once the Load-Store Queue (LSQ) retrieves the real data from the cache, compare it against the LVP's guess.
  - **The Squash**: If the values differ, invoke `squashDueToMispredict()` to clear the speculatively executed instructions and restart from the load.

## Phase 4: Attack Prototyping (The "Gadget")
Proving the vulnerability exists by creating a "Proof of Concept" (PoC) that exploits your new hardware logic.
- **Gadget Design**: A C++ program (`flop_attack.cpp`) using a dispatch table or a struct with a type field.
- **Execution**:
  - **Training Phase**: Loop 250 times with `type=SAFE`.
  - **Trigger Phase**: Switch to `type=MALICIOUS` and use `dc ivac` (ARM cache flush) to ensure the real load is slow.
- **Observation**: Use Konata to capture the window where the CPU executes the "Malicious" path based on the "Safe" prediction before the IEW stage catches the error.

## Phase 5: Managed Speculation Defense
This is the core innovation of the project—improving upon the global "DIT bit" kill-switch.

- **Option A: Sensitive-Context Tagging**:
  - **Mechanism**: Implement a pseudo-instruction or use a reserved ARM system register to "tag" sensitive code blocks (like cryptographic routines or browser sandboxes).
  - **Behavior**: When the tag is active, the LVP is automatically bypassed.

- **Option B: Speculation Depth Throttling**:
  - **Mechanism**: Instructions using LVP data are assigned a "Speculation TTL" (Time-to-Live) counter.
  - **Behavior**: If the load doesn't resolve within ~50 cycles, the dependent instructions are stalled. This stops the "deep" speculation (300+ cycles) required for data leakage while keeping the performance of "shallow" hits.

## Phase 6: Evaluation & Thesis Data
Quantitative analysis for the final report.
- **Performance**: Compare total cycles for:
  - No LVP (Baseline).
  - LVP Enabled (Vulnerable/Fast).
  - Global DIT Defense (Secure/Slow).
  - Your Managed Defense (Secure/Fast).
- **Security**: Verify that the "Attack Gadget" fails to leak data when your defense is active.
